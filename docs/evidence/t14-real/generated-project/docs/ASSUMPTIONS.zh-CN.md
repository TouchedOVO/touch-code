# 架构假设、技术选型与设计决策记录 (Assumptions & Decisions)

本文档系统记录 Space Fractions 在研发与交付过程中所采纳的架构假设、未详述需求的规范化补充、文档逻辑冲突的裁决结果及关键技术选型决策。

---

## 1. 架构假设与工程落地映射

| 假设编号 | 原始设计假设与业务背景 | 系统落地实施方案与技术权衡 |
|---|---|---|
| **A1** | 系统需支持 1000 名用户并发答题。 | 内存核心游戏注册表基于高效的 $O(1)$ 查找设计，API 保持无状态；本地持久化采用轻量级存储。在高并发真实生产部署场景下，建议通过前置负载均衡挂载多个 Node.js Worker 进程并连接外部共享持久化集群。 |
| **A2** | 单轮练习建议时长为 1 小时。 | 服务端不设刚性超时断开限制，以完成 10 道题目的闭环作为单轮练习完备性准则。 |
| **ASM-01** | 每轮练习固定为 10 道题目，答对 +10 分，答错计 0 分，满分 100 分，不设强制答题倒计时。 | 严格落实于 `src/domain/game.js` 领域逻辑中。 |
| **ASM-02** | 学生端无需繁琐注册流程；进入系统时动态分配临时 Guest ID。管理接口通过环境变量配置的安全令牌实施鉴权。 | 学生凭据由 `POST /api/users/guest` 动态颁发；管理员鉴权通过环境配置项 `ADMIN_TOKEN` 解析验证。 |
| **ASM-03** | 题型聚焦于六年级分数四则运算单项选择题，每题包含 4 个备选答案；系统内置种子题库。 | 预置 10 道六年级四则运算分数题目于 `data/seed-questions.json` 中。 |
| **ASM-04** | 服务端持久化必须具备防重启数据丢失能力。 | 研发 `src/repositories/file-store.js`，采用标准原子写入规范（写入临时文件并在操作系统层执行原子重命名），并配套提供针对重启场景的自动化回归测试。 |
| **ASM-05** | 交付物需提供开箱即用的前端交互界面。 | 在 `public/` 目录下交付单页 Web 前端应用（包含答题流、结算报告与无障碍交互）。 |
| **ASM-06** | 架构交付形态采用模块化单体架构（Modular Monolith）。 | 保留原设计中的三大业务服务边界，但统一整合至零外部依赖的原生 Node 运行时中运行，在保障模块解耦的同时简化验证依赖。 |

## 2. 架构设计决策与技术权衡 (Design Trade-offs)

1. **服务架构决策：模块化单体 (Modular Monolith)**  
   - **决策内容**：将架构文档中规划的分布式微服务（Microservices）在代码结构上划分为独立的业务服务模块，但在运行时整合于单一 Node.js 进程中。
   - **权衡理由**：在离线及单机交付检验环境下，微服务架构引入的分布式服务发现、网络治理与多容器编排会显著增加环境搭建与运行不确定性；模块化单体方案在确保领域边界与接口契约完全对齐的前提下，达成了零配置、开箱即用的工程目标。

2. **通信协议决策：原生零依赖 HTTP 服务**  
   - **决策内容**：不引入第三方 Web 框架（如 Express 或 Fastify），基于 Node 原生 `node:http` 模块封装轻量级路由分发器。
   - **权衡理由**：确保工程在任何标准 Node.js 环境下均无需执行 `npm install` 即可立即启动并运行测试，消除了外部网络依赖与依赖版本冲突风险。

3. **存储方案决策：基于原子写入的文件级持久化**  
   - **决策内容**：采用本地文件系统存储 JSON 格式的题目与答题记录，通过“写临时文件 + 操作系统级原子重命名替换”保障写入完整性。
   - **权衡理由**：在当前教学练习与验证规模下，该方案具备出色的读取性能与极简的维护成本，且天然具备跨平台一致性，同时避免了引入外部 PostgreSQL 数据库服务所带来的环境硬性依赖。
